1 What Pi actually is

Ground truth from official docs (pi.dev) — matters because it defines what "customizing" means here.

🪶 Minimal core

Terminal coding harness by Mario Zechner (badlogic). Core = LLM loop + read/write/edit/bash tools. Deliberately ships without MCP, subagents, permission flows, or plan mode.

🧩 Everything is an extension

All missing features are added via TypeScript extensions, skills, and installable packages (pi install npm:… / git:…). This is the "custom harness" surface.

🔁 Claude-compatible skills

Pi reads the exact same SKILL.md frontmatter format as Claude Code. Docs explicitly support pointing settings at ~/.claude/skills.

2 Skills import — mostly free, but triage needed

Zero-copy path exists: one settings line makes Pi read your Claude skills directly. But not every skill survives the trip.

// ~/.pi/agent/settings.json
{
  "skills": ["~/.claude/skills"]   // Pi docs explicitly support this
}
Big win: no migration script, no duplication. Edit a skill once, both Claude Code and Pi see it. The 18 hyperframes-family skills already copied into ~/.pi/agent/skills/ become redundant → delete the copies, keep one source of truth.

4 Ecosystem — don't build what exists

Production-quality packages already cover most of the "custom harness" wishlist. Build custom extensions only for the gaps.

install @spences10/pi-mcp

MCP bridge. Trust model built in: project-local mcp.json untrusted by default — good security posture.

install nicobailon/pi-subagents

Subagents, chains, parallel fan-out, code review, background jobs. Recreates the Claude Code Agent/workflow feel.

install @spences10/pi-redact

Scans tool output for API keys, tokens, connection strings, SSH config before the model sees them. Core of the "no vulnerabilities" requirement.

install @spences10/pi-lsp

Language-server diagnostics into the loop — model sees type errors without running builds. Big quality lift for shipping fast.

optional badlogic/pi-skills

Official skill pack: web search, browser automation, transcription. Fills gaps your Claude skills assume the harness provides (e.g. WebSearch).

optional @spences10/pi-observability + pi-telemetry

Run logging, stats, export. Useful once Pi does company work and you need an audit trail.

5 Custom extensions to actually write

Small, targeted TypeScript — the same pattern as your existing autogit.ts. Each is <100 lines.

🛡️ guardrail.ts

Intercept tool_call: block/confirm destructive bash (rm -rf, force-push, DROP TABLE, prod env writes), deny reads of .env/key files unless confirmed. This is Pi's version of Claude Code's permission system — Pi ships with none.

📋 ship-report.ts

On agent_end, emit your standard end-of-iteration report (what/why/do-now/takeaway) — ports your Claude reporting habit into Pi.

🎛️ provider presets

registerProvider + commands to hot-swap between codex/Anthropic/local Qwen (your llama.cpp setup) per task type — cheap model for grunt work, big model for design.

🔍 skill-lint command

/skill-doctor: scans loaded skills for references to tools Pi doesn't have (Claude-only MCP names) and reports which tier-2 skills still need porting.

7 Phased rollout

1

Skills unification ~15 min

Add "skills": ["~/.claude/skills"] to Pi settings. Delete the 18 duplicated copies in ~/.pi/agent/skills/. Verify with a Pi session that skill descriptions appear in system prompt.

2

MCP bridge ~30 min

  • Install @spences10/pi-mcp
  • ~/.pi/agent/mcp.json: gfi-scout, paper, plan (copy from .claude.json) + Context7 with own key
  • Supabase + Notion official MCP with personal tokens (scoped)
3

Harness packages ~30 min

Install pi-subagents, pi-redact, pi-lsp. Smoke-test each: fan-out a subagent, echo a fake token through bash (must be redacted), open a TS project (must show diagnostics).

4

Custom guardrails ~1–2 h

Write guardrail.ts (destructive-command intercept, .env read confirm). One test file that asserts blocked patterns actually block.

5

Workflow polish iterative

ship-report.ts, provider presets (incl. local Qwen), /skill-doctor, port tier-2 skills as needed. Driven by real daily use, not upfront.

6

Company-grade when needed

Observability/telemetry package, scoped tokens audit, pin all package versions, document the setup as a repo (pi install git: your own config repo = reproducible harness on any machine).

Endgame: phase 6's config repo is the real "custom harness" — your whole Pi setup (extensions + mcp.json + settings + skill pointers) as one installable package. New machine, one command, identical rig.

8 Open questions — decide before Phase 1

1. Primary model on Pi?
Currently gpt-5.5 via codex provider. Keep, or wire Anthropic API key too and swap per task? Recommend: keep gpt-5.5 default, add Anthropic + local Qwen as presets in Phase 5.
2. Which MCP servers does Pi really need day-1?
Proposed: gfi-scout, paper, plan, Context7, Supabase, Notion. Skip Gmail/Canva/media on Pi. Recommend: confirm the skip-list.
3. Company work boundary?
Does company policy allow personal-token MCP (Notion/Supabase) from a local agent? Affects Phase 2 scope. Recommend: personal projects first, company after tokens reviewed.
4. Guardrail strictness?
Block-and-ask (safer, slower) vs log-and-allow (faster, riskier) for destructive commands. Recommend: block-and-ask for git force/rm/db-drop, log-only for the rest.
