Visual implementation proposal

Make Plan mode produce understanding, not chat clutter.

Every Plan-mode request should end with one clear, researched, self-contained HTML file inside the project’s plans/ folder. Implementation starts only after human approval.

Recommended design One narrow publishing tool

Keep normal writes blocked. Allow only a schema-driven tool that renders safe HTML into plans/.

01 / Problem

Current safety is strong. Planning behavior is too thin.

Neura already enforces a real read-only boundary. The missing part is a planning pipeline, a visual output contract, and a safe way to publish one plan file.

Now

Plan mode enables read tools and asks the model for a numbered plan in chat.

Target

Research, explain, publish

The model gathers evidence, builds a compact visual plan, then publishes local HTML.

Done

Human can approve confidently

Opening one file explains what exists, what will change, why, how, and how success will be checked.

02 / Workflow

Six stages, one approval point.

The agent completes the planning loop without interrupting the human repeatedly. Unresolved choices stay inside the plan.

Stage 1Understand

Turn prompt into objective, scope, constraints, and definition of done.

Stage 2Research

Inspect relevant code and docs. Check primary web sources when external facts matter.

Stage 3Decide

Choose a recommended approach. Expose only choices that need human judgment.

Stage 4Compose

Write simple sections, real file paths, useful visuals, steps, risks, and checks.

Stage 5Publish

Validated renderer creates one self-contained HTML file in plans/.

Stage 6Wait

Show file path. Stop before implementation until Rajveer approves or requests edits.

Research rule: every plan gets an evidence pass. Local code and documentation are always checked. Web research is required when the topic depends on current libraries, APIs, standards, products, or outside facts. The plan records the sources that materially changed its direction.
03 / Contract

Every HTML plan follows the same reading order.

Consistency makes plans fast to scan. Limits prevent a “50-paragraph document” while leaving room for genuinely complex work.

Required content

  • Summary: what we are doing, why, and what “done” means.
  • Current state: evidence from real code and documentation.
  • Target state: recommended direction and key decisions.
  • Visual explanation: at least one meaningful flowchart, comparison, boundary map, or infographic.
  • Ordered steps: what changes, where, why, and proof for each step.
  • Scope and risks: included work, deferred work, safety concerns.
  • Verification: automated checks plus one realistic end-to-end journey.
  • Sources and open decisions: short, final, easy to review.

Writing rules

  • Use simple English and one idea per paragraph.
  • Lead with outcome. Explain unfamiliar technical terms once.
  • Name actual files, symbols, commands, and existing helpers.
  • Use 5–8 implementation steps for normal work.
  • Keep the default plan near 800–1,500 words. Put deep evidence in collapsible detail when needed.
  • Use 1–3 visuals. Every visual must answer a real question.
  • No decorative hero art, fake dashboards, or repeated summaries.
  • Plan must stand alone without chat history.
Suggested improvement: treat word counts as a target, not a hard failure. Large migrations may need more detail. Readability, evidence, and decision clarity matter more than an arbitrary limit.
04 / Safety

Use structured plan data, then render trusted HTML.

The model should not receive a general-purpose write exception. A dedicated publish_plan tool accepts bounded plan data and owns all filesystem work.

Research side

read / grep / find / ls
allowlisted read-only shell
approved research connector
questionnaire when essential

Single write seam

publish_plan
Input: structured sections + visual blocks
Renderer: fixed local HTML/CSS template
Output: project root / plans / safe slug
Result: path + SHA-256 + validation summary

Still blocked

generic write and edit
mutating shell commands
paths outside plans/
scripts, iframes, remote assets

Plan mode remains read-only except for one validated artifact published inside the current project.

Publisher rules

  • Find nearest project root containing .git; use ctx.cwd only when no project root exists.
  • Create only plans/<safe-slug>-plan.html.
  • Reject absolute paths, traversal, symlink escapes, and non-HTML extensions.
  • Create a new file. A revision may replace only the plan created by this session.
  • Serialize writes with Pi’s file mutation queue and return a content hash.

Renderer rules

  • Static, self-contained HTML and CSS. No JavaScript needed in v1.
  • Escape all text fields before rendering.
  • Render only known blocks: prose, comparison, flow, boundary map, file map, steps, risks, checks, decisions, sources.
  • Require at least one visual block and one verification block.
  • Keep source URLs as normal links; never load remote fonts, images, or scripts.

06 / Choices

Recommended v1 decisions.

These defaults keep the first version useful and safe. They can change before implementation.

Artifact format
Self-contained static HTML. Easy to open locally, portable, no hosted dependency.
Write mechanism
Structured publish_plan tool. Safer and more consistent than granting generic write access.
Location
Nearest project root / plans/. Fall back to current working folder only outside a project.
Filename
<topic-slug>-plan.html. Add a numeric suffix on collision. Revise only the session-owned file.
Research
Local evidence always; primary web sources when relevant. Do not browse merely to decorate the sources list.
Interaction
One final approval gate. Ask earlier only when an unresolved choice would materially change architecture or scope.
Later version
Optional interactive comments, richer diagram layouts, browser auto-open, and plan-to-execution progress tracking.
07 / Proof

Verification must prove safety and usefulness.

Passing unit tests is not enough. A human must be able to open the file and understand the proposed work quickly.

  • node scripts/verify-harness.mjs passes.
  • Plan mode exposes research tools plus publish_plan only.
  • Generic write, edit, and mutating shell remain blocked.
  • Publisher cannot escape project plans/.
  • Existing plans cannot be overwritten by a new session.
  • Generated HTML has summary, visual, steps, verification, and sources.
  • HTML opens without network access or JavaScript.
  • Desktop and mobile layouts remain readable.
  • A reviewer can explain “now, target, steps, proof” after one read.
  • YOLO and Human Away tests show no behavior change.
08 / Evidence

Evidence used for this proposal.

Repository facts establish the current gap. Official Pi documentation confirms the extension points needed for the fix.

  1. agent/extensions/modes.ts — current Plan prompt requests a numbered plan; active tools are fixed to read-only exploration.
  2. agent/extensions/guardrail.ts and agent/neura/action-policy.ts — Plan calls fail closed unless tool and shell action are allowlisted.
  3. scripts/verify-harness.mjs — existing regression checks already prove Plan restrictions and provide the right place for publisher tests.
  4. docs/CHANGELOG.md and existing plans/ — this project explicitly prefers local HTML plans over the hosted Plan service.
  5. Official Pi extension documentation — before_agent_start receives the prompt; extensions can register custom tools and control active tools with setActiveTools().
  6. Official Pi Plan-mode example — confirms read-only tool filtering, prompt injection, state persistence, and the normal plan-to-execution handoff pattern.
